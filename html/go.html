第 1 章

运行架构：环境规划与部署方案（Go 技术栈）

本章回答“系统跑在哪里、怎么跑”：测试 / 预发布 / 生产三套环境如何划分与隔离，以及两种落地方案——方案 A 全自建、方案 B 阿里云，并给出 AWS、Azure 的对应关系。 应用层（Go 服务代码、镜像、Helm Chart、GitOps 流程）在所有方案中完全一致，差异只在平台层。 本章的环境规划、部署拓扑与 Spring Cloud 版 相同，Go 版特有的运行差异见 1.9。

#1.1 总体设计原则

原则 含义 落地方式
一次构建，处处部署 同一个镜像（同一 digest）从测试晋级到生产，环境差异不进镜像 配置分三处：GitOps values（规模）、Nacos 命名空间（业务配置）、K8s Secret（凭据）
无状态计算进 K8s，有状态数据靠专业设施 应用 Pod 可随时重建；数据库等有状态组件需要专门的高可用与备份手段 自建：数据库放 K8s 外物理机/虚机；阿里云：RDS / PolarDB / Tair / 云消息队列
环境同构 预发布与生产拓扑、组件版本、配置项一致，只是规模更小 同一套 Helm Chart + 环境 values；Nacos 配置项逐项对齐
默认安全 最小权限、密钥不落地、网络默认拒绝 NetworkPolicy、非 root 容器、External Secrets、RRSA / Vault
可观测先行 上线即有指标、链路、日志、告警 所有服务通过 pkg/observability、pkg/server 统一接入 OpenTelemetry + Prometheus
声明式与可追溯 环境状态以 Git 为准，变更可审计、可回滚 GitOps（Argo CD），生产手动 Sync + 审批

#1.2.3 环境差异放在哪里

  • 镜像里只有与环境无关的默认值，例如超时、连接池、日志格式开关；
  • GitOps values 描述“部署形态”：副本数、资源、HPA、Ingress 域名、采样率；
  • Nacos 描述“业务行为”，可以热更新；
  • Secret 只放凭据，从 Vault / 阿里云 KMS 凭据管家同步，永不进 Git 和 Nacos；
  • platform-env 是平台团队维护的“地址簿”，每个集群一份（见 acme-go/deploy/k8s/platform/）。

#1.3.2 关键设计点

  1. 数据库不进 K8s。 数据库的高可用、备份、扩容、内核调优都需要专门的手段；在 IDC 里放在物理机上更可控。消息与缓存可以由 Operator（Strimzi、RabbitMQ Cluster Operator）管理，但必须放在专用节点池（污点隔离、本地 SSD），避免与业务 Pod 争抢资源。
  2. 服务直连 Pod IP。 服务注册到 Nacos 的是 Pod IP，并按协议分别注册为 <服务>.http 与 <服务>.grpc；服务间 gRPC 调用直连 Pod，不经过 kube-proxy；网关按 <服务>.http 发现实例。因此 Pod 网络需与 Nacos 所在网络互通（Calico BGP 或 Overlay 均可，需放通 Nacos 8848/9848 端口）。
  3. 三个集群 + 一个管理集群。 测试、预发布、生产各一个业务集群；GitLab、Harbor、Argo CD、Vault 放在管理集群（或虚机），所有环境共用。生产集群的 API Server 只对管理集群和堡垒机开放。
  4. 双机房（可选）。 生产 K8s Worker 跨两个机房（同城，<2ms），MySQL MGR 三节点分布在两机房 + 仲裁机房；Kafka 设置 broker.rack 实现跨机房副本。
  5. 备份。 MySQL 用 XtraBackup 全量 + binlog 增量（RPO ≤ 5 分钟），PostgreSQL 用 pgBackRest + WAL 归档；K8s 资源用 Velero；全部备份异地存放并每季度做恢复演练。

#1.4.2 多账号与网络布局

#1.4.3 关键设计点

  1. 有状态全部托管。 数据库、缓存、消息、Nacos 使用云产品，ACK 只运行无状态服务——运维重心从“维护中间件”转到“用好中间件”。
  2. 入口二选一。 默认 ALB → ALB Ingress → acme-gateway（Go），网关逻辑在代码里，可测试、可灰度；如果希望把鉴权、限流也交给云产品，可用 MSE 云原生网关（基于 Higress）替换 ALB Ingress，此时 Go 网关可保留做业务路由与灰度，或整体下线。
  3. RRSA 免密钥。 Pod 通过 RRSA（RAM Roles for Service Accounts）获取临时凭证访问 KMS、OSS 等，代码与配置中不出现 AccessKey。Helm values 的 serviceAccount.annotations 用于绑定角色。
  4. 可观测接入零改造。 服务通过 OTLP 上报链路，只需把 OTEL_EXPORTER_OTLP_TRACES_ENDPOINT 指向 ARMS 接入点；指标是管理端口的 /metrics，由 ARMS Prometheus 采集；日志以 JSON 输出到 stdout，由 LoongCollector 采集到 SLS。
  5. 成本优化。 测试环境节点池使用抢占式实例 + ECI 弹性；预发布非工作时间缩容（定时 HPA 或 CronHPA）；生产预留实例 / 节省计划覆盖基线容量。
  6. 容灾。 生产三可用区部署；RDS 跨地域备份、OSS 跨区域复制；需要两地三中心时采用 PolarDB 全球数据库 + 异地 ACK 集群冷备 / 温备。

#1.5 AWS / Azure 对应方案

迁移到 AWS / Azure 时需要关注的差异：

差异点 处理方式
无托管 Nacos 在 EKS / AKS 内用 StatefulSet 部署 Nacos 集群（存储用托管 MySQL）；或改用 K8s 原生服务发现（Kratos 的 kubernetes registry 或 Headless Service DNS）+ ConfigMap 配置，见第 2 章 2.5
RabbitMQ（Azure） Azure 无托管 RabbitMQ：在 AKS 用 RabbitMQ Cluster Operator 部署，或优先选 Kafka（Event Hubs 提供 Kafka 协议端点）
身份 AWS 用 IRSA / EKS Pod Identity，Azure 用 Workload Identity，均通过 serviceAccount.annotations 配置
链路 AWS 用 ADOT（OpenTelemetry 发行版）+ X-Ray，Azure 用 Application Insights（支持 OTLP），只改 OTLP 地址

#2.5.1 注册方式

服务启动后，Kratos 应用把每个传输端点注册为一个 Nacos 服务（实现见 contrib/registry/nacos）：

#2.5.2 为什么在 K8s 上仍然使用 Nacos

理由与 Spring Cloud 版一致：灰度需要实例元数据、跨集群 / 混合部署需要统一注册中心、配置中心需要审批与灰度发布能力，并且阿里云 MSE 提供托管。Go 版额外的好处是：与 Spring Cloud 服务注册到同一个 Nacos 后可以互相发现（服务名规则不同，见 2.16）。

不想维护 Nacos 时（如 AWS / Azure）：把 pkg/registry 换成 Kratos 的 kubernetes registry，或直接使用 Headless Service DNS（dns:///order-service-grpc.acme.svc:9090）；配置改为 ConfigMap 文件源。业务代码不受影响。

#2.7.1 为什么自研一个 Go 网关

Go 生态没有与 Spring Cloud Gateway 同等地位的“框架内网关”，常见做法有两种：使用 APISIX / Higress / Kong 等独立网关产品，或用标准库写一个精简网关。本方案选择后者（约 400 行），因为：

  • 鉴权、灰度、错误码与业务服务共用 pkg/auth、pkg/selector/gray、pkg/result，规则只写一份；
  • 网关逻辑和业务代码一起评审、测试、发布；
  • 需要更强的流量治理（WAF 插件、插件市场、可视化）时，可以平滑切换到 APISIX / Higress（阿里云 MSE 云原生网关基于 Higress），把 JWT 校验、限流迁过去，Go 网关只保留灰度与业务路由，或整体下线。

#2.8.1 契约

pkg/client 的中间件链（顺序有意义）：

顺序 中间件 作用
1 recovery 防止 panic 扩散
2 tracing 注入 traceparent，链路贯穿
3 metadata 透传 x-gray-tag、authorization、x-md-*
4 remoteErrors 还原下游错误：4xx 业务错误码原样返回；熔断 / 不可用 / 超时 → C0503；其它 → C0001

#2.8.3 错误在服务间如何传递

Kratos 错误同时携带 HTTP 状态（Code）与业务错误码（Reason）。经 gRPC 传输时放在 ErrorInfo 中，调用方 errors.FromError 即可原样还原，无需像 Feign 那样解析响应体。冒烟测试验证了这条链路：user-service 返回 404 A1001 → order-service 的防腐层翻译为 422 A2002；user-service 宕机 → 503 C0503。

#2.9 容错

位置 机制 关键参数
网关路由 gobreaker（失败率熔断） 最近 60s 请求数 ≥ 50 且失败率 ≥ 50% 打开，10s 后半开
服务间 gRPC Kratos circuitbreaker.Client（Google SRE 自适应限流算法，按 operation 分组） 根据成功率自动丢弃部分请求，无需手工阈值
超时 context 截止时间（网关 10s、服务间 3s） 下游超时向上游传递，避免“等待已经无人关心的结果”

#2.10 消息驱动：Watermill

#2.10.1 驱动选择

MQ_DRIVER 在运行时选择（同一个镜像同时包含两种驱动）：

驱动 发布 消费组
kafka Sarama 幂等生产者（acks=all），消息 key = acme_event_key Kafka consumer group = 服务名
rabbitmq 每个 topic 一个 fanout 交换机 每个消费组一个持久化队列 <topic>_<服务名>
gochannel 进程内总线，仅测试使用 —

与 Java 版的差异：Spring Cloud Stream 的 RabbitMQ Binder 以事件类型作为 routing key，消费者只绑定关心的类型；Watermill 的 AMQP 适配器按 topic 生成 routing key，因此 Go 版使用 fanout，消费者按 acme_event_type 头过滤（与 Kafka 的处理方式相同）。

#2.10.2 发布：事务发件箱

#2.10.4 事件头与载荷

事件头与 Java 版完全相同：acme_event_id、acme_event_type、acme_event_source、acme_event_time、acme_event_key。载荷是 protojson 编码的 proto 消息（如 OrderCreated），字段为小驼峰，消费方使用 DiscardUnknown 容忍新增字段。

#3.2 仓库与分支

  • 单仓单模块（本工程默认）：acme-go 是一个 Go module，所有服务共享 go.mod，依赖版本天然一致，跨服务重构一次提交完成；CI 按变更路径只构建受影响的服务。

#3.5 API 与 Protobuf 规范

# 规则
1 所有接口先写 proto，再生成代码；生成代码与 proto 一起提交，CI 检查二者一致 🔒
2 buf lint（STANDARD 规则）🔒；buf breaking 与 main 比较，禁止删除字段、修改字段编号或类型 🔒
3 字段名在 proto 中用 snake_case，JSON 输出为 lowerCamelCase（protojson 默认）
4 对外接口用 google.api.http 注解，前缀 /api/v<n>/，资源复数名词；集群内接口只定义为 *InternalService，不加 HTTP 注解，因此网关不可达 🔒
5 int64 在 JSON 中输出为字符串（protojson 默认，避免 JS 精度丢失）；金额用字符串表示的十进制数（服务内用 shopspring/decimal）
6 时间用 google.protobuf.Timestamp（JSON 为 RFC 3339）
7 分页请求 page_no（从 1 开始）、page_size（≤100）；响应 total、page_no、page_size、records
8 统一响应体 {code, message, data, traceId} 与错误码规则同 Spring Cloud 版，由 pkg/result 编码 🔒；成功统一 HTTP 200（Kratos 约定），失败使用与错误码一致的 HTTP 状态
9 业务失败返回 biz.ErrXxx.New(args...) / errorx.BadRequest.Msg("...")，不要返回 fmt.Errorf 字符串错误给调用方 👀；未知错误统一 B0001，原始错误只记录在日志中 🔒
10 字段只增不删；废弃字段标注 reserved，不复用编号

#3.6 Go 编码规范

# 规则
1 gofmt / goimports 格式化 🔒；go vet 与 golangci-lint（.golangci.yml）通过 🔒（CI）
2 context.Context 作为第一个参数并逐层传递，不保存到结构体，不传 nil
3 错误必须处理；包装时用 fmt.Errorf("...: %w", err) 保留错误链，判断用 errors.Is / As
4 不在库代码中 panic；服务入口与中间件有 recovery 兜底
5 不使用全局可变状态与 init() 副作用；依赖通过构造函数显式传入（组装集中在 internal/server）
6 导出的标识符写注释；注释说明“为什么”，而不是复述代码
7 接口小而专注（1~3 个方法），定义在使用方；返回具体类型，接收接口
8 日志用 log.NewHelper(logger).WithContext(ctx)，自动带 trace_id；键值对形式 Infow("msg", "...", "order_id", id)
9 不打印密码、令牌、完整手机号 / 身份证 / 银行卡 👀
10 资源（rows、resp.Body、文件）用 defer 关闭 🔒（bodyclose、sqlclosecheck）

#3.7 并发规范

# 规则
1 每个 goroutine 都要有明确的退出条件（ctx.Done() 或通道关闭），不允许“发射后不管” 👀
2 长期运行的后台任务（发件箱投递、消费者、定时任务）实现 transport.Server，交给 Kratos App 管理启停（参考 mq.Relay、mq.Router）
3 并发处理一批任务用 errgroup 并设置并发上限（SetLimit），禁止无界创建 goroutine
4 共享数据优先用通道或 sync/atomic（如网关的 atomic.Pointer 配置热更新）；必须加锁时锁的范围尽量小，不在持锁时做 I/O
5 测试统一带 -race 运行 🔒（CI）

#3.8 服务间调用规范

# 规则
1 只依赖对方 api/ 中的 gRPC 客户端，禁止复制对方的结构体或手写 HTTP 调用 👀
2 连接通过 pkg/client.Dial 创建（发现、灰度、超时、熔断、元数据透传、错误还原）🔒
3 下游调用放在数据库事务之外 👀（参考 OrderUsecase.Create）
4 在 data 层做防腐适配，把下游错误翻译为本服务语义（参考 buyerGateway）👀
5 不在循环中逐条调用，提供批量接口；同步调用链深度 ≤ 3，更长的流程改为事件驱动 👀
6 一个服务进程内对同一下游只建一个 *grpc.ClientConn，在启动时创建、退出时关闭

#3.9 数据库规范

数据库设计规范（一服务一库、公共字段、雪花 / Sonyflake 主键、索引、禁止外键与跨库 JOIN、大表 Online DDL、双数据库兼容写法）同 Spring Cloud 版。Go 特有部分：

# 规则
1 PO 结构体内嵌 database.Model（id、created_at、updated_at、deleted 逻辑删除、version 乐观锁）🔒
2 仓储通过 database.DB(ctx, r.db) 取连接，自动加入当前事务；事务只在用例层用 Transaction.InTx 开启 👀
3 禁止在生产使用 GORM AutoMigrate；表结构只由 goose 脚本管理 🔒（工程中没有调用）
4 迁移脚本放在 migrations/{mysql,postgres,sqlite}/，文件名 00001_<描述>.sql，含 -- +goose Up / Down；已在共享环境执行过的脚本禁止修改
5 sqlite/ 目录只用于测试，结构须与 mysql / postgres 保持一致 👀
6 主键 ID 在应用侧生成（database.NextID()），便于在事务前拿到 ID、写入事件
7 唯一约束冲突用 errors.Is(err, gorm.ErrDuplicatedKey) 判断（已开启 TranslateError）
8 查询必须带条件与分页上限；原生 SQL 只用参数绑定，禁止拼接用户输入

#3.10 消息规范

与 Spring Cloud 版相同的规则：发布必须走发件箱（mq.Outbox.Publish 在事务外调用会直接返回错误 🔒）、消费必须幂等（mq.Idempotent）、事件是过去式事实、契约只做向后兼容修改、消息头使用 acme_event_*（不要用 ce_ 前缀）、重试耗尽进入死信并告警、Topic 由平台创建。

Go 特有：事件契约用 proto 定义在 api/<领域>/v1/events.proto，载荷用 protojson 编码；消费方用 protojson.UnmarshalOptions{DiscardUnknown: true} 容忍新增字段。

#4.4.3 用例：远程调用在事务外，订单与事件同事务

// app/order/internal/biz/order.go
func (uc *OrderUsecase) Create(ctx context.Context, cmd CreateOrderCommand) (*Order, error) {
	ok, err := uc.buyers.CanPlaceOrder(ctx, cmd.UserID)   // ① gRPC，在事务外
	if err != nil {
		return nil, err
	}
	if !ok {
		return nil, ErrBuyerNotAvailable.New()
	}
	o := NewOrder(uc.repo.NextID(), cmd.UserID, cmd.ProductCode, cmd.Quantity, cmd.Amount, uc.now())
	err = uc.tx.InTx(ctx, func(ctx context.Context) error { // ② 本地事务
		if err := uc.repo.Add(ctx, o); err != nil {
			return err
		}
		return uc.events.OrderCreated(ctx, o)              // ③ 写发件箱
	})
	if err != nil {
		return nil, err
	}
	return o, nil
}

#4.4.4 防腐层：把下游错误翻译成本域语义

// app/order/internal/data/order.go
func (g *buyerGateway) CanPlaceOrder(ctx context.Context, userID int64) (bool, error) {
	u, err := g.users.GetUser(ctx, &userv1.GetUserRequest{Id: userID})
	if err != nil {
		se := errorx.Normalize(err)
		if se.Code < 500 {
			return false, nil   // 下游业务错误（如 A1001 用户不存在）→ 不可下单
		}
		return false, se        // 下游故障（C0001 / C0503）→ 原样返回
	}
	return u.Status == "ACTIVE", nil
}

#4.4.5 灰度筛选（网关与 gRPC 共用一套规则）

go
// pkg/selector/gray/gray.go
func Select[T any](nodes []T, tag string, meta func(T) map[string]string) []T {
	var stable, gray []T
	for _, n := range nodes {
		t := meta(n)[MetadataKey]
		switch {
		case t == "":
			stable = append(stable, n)
		case tag != "" && t == tag:
			gray = append(gray, n)
		}
	}
	if len(gray) > 0 {
		return gray       // 带标签的请求 → 同标签实例
	}
	if len(stable) == 0 {
		return nodes      // 全部为灰度实例时不过滤，可用性优先
	}
	return stable         // 普通请求 → 只走稳定实例
}

#4.4.6 幂等消费

go
// pkg/mq/consumer.go
func (i *Idempotent) Handler(fn func(ctx context.Context, msg *message.Message) error) message.NoPublishHandlerFunc {
	return func(msg *message.Message) error {
		id := msg.Metadata.Get(HeaderID)
		err := i.tx.InTx(msg.Context(), func(ctx context.Context) error {
			record := ConsumedEvent{Consumer: i.consumer, EventID: id, ConsumedAt: time.Now().UTC()}
			if err := database.DB(ctx, i.db).Create(&record).Error; err != nil {
				return err
			}
			return fn(ctx, msg)   // 业务写入与登记在同一事务
		})
		if errors.Is(err, gorm.ErrDuplicatedKey) {
			return nil            // 重复投递：确认并跳过
		}
		return err
	}
}
