第 1 章

运行架构：环境规划与部署方案

本章回答“系统跑在哪里、怎么跑”：测试 / 预发布 / 生产三套环境如何划分与隔离，以及两种落地方案——方案 A 全自建、方案 B 阿里云，并给出 AWS、Azure 的对应关系。 应用层（Spring Cloud 代码、镜像、Helm Chart、GitOps 流程）在所有方案中完全一致，差异只在平台层。

#1.1 总体设计原则

原则 含义 落地方式
一次构建，处处部署 同一个镜像（同一 digest）从测试晋级到生产，环境差异不进镜像 配置分三处：GitOps values（规模）、Nacos 命名空间（业务配置）、K8s Secret（凭据）
无状态计算进 K8s，有状态数据靠专业设施 应用 Pod 可随时重建；数据库等有状态组件需要专门的高可用与备份手段 自建：数据库放 K8s 外物理机/虚机；阿里云：RDS / PolarDB / Tair / 云消息队列
环境同构 预发布与生产拓扑、组件版本、配置项一致，只是规模更小 同一套 Helm Chart + 环境 values；Nacos 配置项逐项对齐
默认安全 最小权限、密钥不落地、网络默认拒绝 NetworkPolicy、非 root 容器、External Secrets、RRSA / Vault
可观测先行 上线即有指标、链路、日志、告警 所有服务通过 acme-starter-base 统一接入 Micrometer + OpenTelemetry
声明式与可追溯 环境状态以 Git 为准，变更可审计、可回滚 GitOps（Argo CD），生产手动 Sync + 审批

#1.2.3 环境差异放在哪里

  • 镜像里只有与环境无关的默认值，例如超时、连接池、日志格式开关；
  • GitOps values 描述“部署形态”：副本数、资源、HPA、Ingress 域名、采样率；
  • Nacos 描述“业务行为”，可以热更新；
  • Secret 只放凭据，从 Vault / 阿里云 KMS 凭据管家同步，永不进 Git 和 Nacos；
  • platform-env 是平台团队维护的“地址簿”，每个集群一份（见 acme-cloud/deploy/k8s/platform/）。

#1.3.2 关键设计点

  1. 数据库不进 K8s。 数据库的高可用、备份、扩容、内核调优都需要专门的手段；在 IDC 里放在物理机上更可控。消息与缓存可以由 Operator（Strimzi、RabbitMQ Cluster Operator）管理，但必须放在专用节点池（污点隔离、本地 SSD），避免与业务 Pod 争抢资源。
  2. 服务直连 Pod IP。 服务注册到 Nacos 的是 Pod IP，服务间调用不经过 kube-proxy；网关通过 lb://服务名 解析。因此 Pod 网络需与 Nacos 所在网络互通（Calico BGP 或 Overlay 均可，需放通 Nacos 8848/9848 端口）。
  3. 三个集群 + 一个管理集群。 测试、预发布、生产各一个业务集群；GitLab、Harbor、Argo CD、Vault 放在管理集群（或虚机），所有环境共用。生产集群的 API Server 只对管理集群和堡垒机开放。
  4. 双机房（可选）。 生产 K8s Worker 跨两个机房（同城，<2ms），MySQL MGR 三节点分布在两机房 + 仲裁机房；Kafka 设置 broker.rack 实现跨机房副本。
  5. 备份。 MySQL 用 XtraBackup 全量 + binlog 增量（RPO ≤ 5 分钟），PostgreSQL 用 pgBackRest + WAL 归档；K8s 资源用 Velero；全部备份异地存放并每季度做恢复演练。

#1.4.2 多账号与网络布局

#1.4.3 关键设计点

  1. 有状态全部托管。 数据库、缓存、消息、Nacos 使用云产品，ACK 只运行无状态服务——运维重心从“维护中间件”转到“用好中间件”。
  2. 入口二选一。 默认 ALB → ALB Ingress → acme-gateway（Spring Cloud Gateway），网关逻辑在代码里，可测试、可灰度；如果希望把鉴权、限流也交给云产品，可用 MSE 云原生网关 替换 ALB Ingress（此时 Spring Cloud Gateway 可保留做业务路由，或下沉其职责）。
  3. RRSA 免密钥。 Pod 通过 RRSA（RAM Roles for Service Accounts）获取临时凭证访问 KMS、OSS 等，代码与配置中不出现 AccessKey。Helm values 的 serviceAccount.annotations 用于绑定角色。
  4. 可观测接入零改造。 服务通过 OTLP 上报链路，只需把 OTEL_EXPORTER_OTLP_TRACES_ENDPOINT 指向 ARMS 接入点；指标仍是 /actuator/prometheus，由 ARMS Prometheus 采集；日志输出 JSON 到 stdout，由 LoongCollector 采集到 SLS。
  5. 成本优化。 测试环境节点池使用抢占式实例 + ECI 弹性；预发布非工作时间缩容（定时 HPA 或 CronHPA）；生产预留实例 / 节省计划覆盖基线容量。
  6. 容灾。 生产三可用区部署；RDS 跨地域备份、OSS 跨区域复制；需要两地三中心时采用 PolarDB 全球数据库 + 异地 ACK 集群冷备 / 温备。

#1.5 AWS / Azure 对应方案

迁移到 AWS / Azure 时需要关注的差异：

差异点 处理方式
无托管 Nacos 在 EKS / AKS 内用 StatefulSet 部署 Nacos 集群（存储用托管 MySQL）；或改用 Spring Cloud Kubernetes（K8s Service 发现 + ConfigMap 配置，见 2.3.3）
RabbitMQ（Azure） Azure 无托管 RabbitMQ：在 AKS 用 RabbitMQ Cluster Operator 部署，或优先选 Kafka（Event Hubs 提供 Kafka 协议端点）
身份 AWS 用 IRSA / EKS Pod Identity，Azure 用 Workload Identity，均通过 serviceAccount.annotations 配置
链路 AWS 用 ADOT（OpenTelemetry 发行版）+ X-Ray，Azure 用 Application Insights（支持 OTLP），只改 OTLP 地址

#1.6 方案对比与选型建议

维度 方案 A 全自建 方案 B 阿里云
初始投入 高：硬件、机房、网络、各组件高可用搭建 低：按需开通
长期成本 规模大且稳定时更低 弹性好；规模很大时需用预留实例控制成本
运维人力 需要 DBA、中间件、K8s 专职团队 平台团队 2~3 人即可支撑
弹性 受限于机房容量 分钟级扩容（ECI / 节点池自动伸缩）
高可用 / 容灾 依赖自建能力与演练 多可用区开箱即用，跨地域方案成熟

#2.3 服务注册与发现：Nacos Discovery

#2.3.1 为什么在 K8s 上仍然使用 Nacos

K8s 自带 Service + DNS 也能做服务发现。两种方案的对比：

维度 Nacos Discovery（本方案默认） K8s Service / Spring Cloud Kubernetes

实例元数据 支持（gray-tag、version、zone），是全链路灰度的基础 需要读取 Pod label，依赖 RBAC 权限
跨集群 / 混合部署 天然支持（K8s 内外、多集群都注册到同一 Nacos） 只能看到本集群
配置中心 同一套组件提供，支持灰度发布配置、历史回滚、权限 ConfigMap，需要自建审批与审计
阿里云 MSE Nacos 托管，并可叠加 MSE 服务治理 —
额外运维 需维护 Nacos 集群（云上托管则无） 无

#2.7 容错：Spring Cloud CircuitBreaker（Resilience4j）

位置 作用 关键配置
网关路由 下游整体不可用时快速失败，返回 C0503 resilience4j.timelimiter.configs.default.timeout-duration: 8s
Feign 调用 单个下游异常时保护调用方线程与连接 failure-rate-threshold: 50、slow-call-duration-threshold: 2s、wait-duration-in-open-state: 10s

两条重要约定（20-feign.yml）：

  1. 熔断器忽略 BizException：下游返回的“用户不存在”等 4xx 是正常业务结果，不能把熔断器打开；
  2. Feign 场景关闭 TimeLimiter（spring.cloud.circuitbreaker.resilience4j.disable-time-limiter: true）：超时交给 HTTP 客户端，调用保持在当前线程，RequestContextHolder 中的请求头才能被透传。

重试：只对幂等的 GET 请求开启（LoadBalancer 的 spring.cloud.loadbalancer.retry），写请求不自动重试，由业务幂等键 + 客户端重试保证。

替代方案：阿里云上可使用 Sentinel（Spring Cloud Alibaba Sentinel）或 MSE 服务治理，获得控制台化的流控、热点参数限流与全链路灰度；与 Resilience4j 二选一，不要叠加。

#2.8.1 Kafka 还是 RabbitMQ

场景 推荐

    return message -> {
        if (!OrderEventTypes.ORDER_CREATED.equals(message.getHeaders().get(EventHeaders.TYPE, String.class))) {
            return;
        }
        idempotentConsumer.consume(message, notificationAppService::onOrderCreated);
    };
}

#2.8.3 事务发件箱（Transactional Outbox）

  • 投递语义是至少一次：Relay 发送成功但更新状态前崩溃，会重发；因此消费端必须幂等（IdempotentConsumer 以 consumer + event_id 为主键去重）；
  • outbox_event、consumed_event 表结构见各服务的 Flyway 脚本，已发送事件按天归档清理。

#2.8.4 事件头规范

消息头 含义
acme_event_id 事件 ID（UUID），消费幂等键
acme_event_type 事件类型，如 order.created；RabbitMQ 的 routing key
acme_event_source 来源服务名
acme_event_time 发生时间（ISO-8601）
acme_event_key 聚合根 ID；Kafka 消息 key，保证同一聚合有序

⚠️ 不要使用 ce_ / ce- 前缀：Spring Cloud Function 会把这类头识别为 CloudEvents 属性并改写，消费端读不到原值（初始工程搭建过程中实际踩到并已规避）。

#2.9 分布式事务

场景 方案
跨服务的数据最终一致（绝大多数场景） Outbox + 幂等消费 + 补偿（本工程内置）
多步骤长流程（下单 → 扣库存 → 支付 → 发货） Saga：每步发布事件，失败时发布补偿事件；编排式可用状态机（如 Spring State Machine）实现
必须强一致且跨库的少数场景 Seata（AT / TCC 模式；阿里云可用 MSE 托管 Seata）——引入前需评审，它会显著增加锁冲突与运维复杂度

原则：先从业务上避免分布式事务（合理划分聚合与服务边界），其次最终一致，最后才是强一致。

#2.10 认证与授权：Spring Authorization Server + Resource Server

代码：acme-auth、acme-starter-security、acme-gateway/config/GatewaySecurityConfig

约定 说明
客户端 acme-web：授权码 + PKCE（公共客户端，无密钥）；acme-internal：客户端凭证（后台任务、系统集成）
令牌声明 uid（当前用户 ID，资源服务以此识别用户，绝不信任请求参数中的 userId）、roles（映射为 ROLE_xxx）、scope（映射为 SCOPE_xxx）
两级校验 网关做认证（拒绝无效令牌），服务做授权（@PreAuthorize），并且服务自己也校验 JWT（纵深防御，防止绕过网关的集群内访问）
服务间调用 用户上下文中的调用透传用户令牌（HeaderRelayRequestInterceptor）；无用户上下文的后台任务使用 acme-internal 客户端凭证
签名密钥 RSA 密钥对由 Vault / KMS 管理，以 PEM 文件挂载（acme.auth.jwk.*），多副本必须共享同一密钥；轮换时新旧 kid 并存一个令牌有效期

Spring Cloud 团队开发规范

规范的目标是让 30100 人、1050 个服务的团队写出“看起来像一个人写的”代码。 能自动化的规范都已经固化在初始工程里（starter 默认值、ArchUnit、CI 检查）；本章说明为什么以及自动化覆盖不到的部分。 标记说明：🔒 由工程或 CI 强制；👀 代码评审检查。

#3.1 服务拆分与命名

#3.1.1 拆分原则

  • 按业务能力 / 限界上下文拆分（用户、订单、支付、库存、通知……），而不是按技术层拆分（不要出现 dao-service、common-service）；
  • 一个服务由一个团队负责，一个团队可以负责多个服务；
  • 一个服务独占自己的数据库，其它服务只能通过 API 或事件获取它的数据；
  • 拆分粒度宁粗勿细：初期 5~10 个服务即可，出现明确的独立扩缩容、独立发布、团队边界需求时再拆。

#3.4 分层规范

#3.5.1 URL 与方法

规则 示例

#3.5.2 统一响应与错误码

所有接口返回 Result<T>，同时使用正确的 HTTP 状态码 🔒：

json
{ "code": "A2002", "message": "下单用户不存在或已被禁用", "data": null, "traceId": "4bf92f3577b34da6a3ce929d0e0e4736" }
规则 说明
错误码格式 5 位：首字母 A 调用方错误 / B 本系统错误 / C 第三方或下游错误，后 4 位数字；成功为 00000（参考《阿里巴巴 Java 开发手册》）
号段 平台 0000-0999；每个服务 1000 个号段，在服务的 XxxErrorCode 枚举中定义
HTTP 状态 由 ErrorCode.httpStatus() 决定：400 参数、401 未认证、403 无权限、404 不存在、409 冲突、422 业务规则不满足、429 限流、5xx 系统错误
业务失败 抛 BizException(ErrorCode, args...)，由全局异常处理器转换；不要在 Controller 里 try/catch 拼 Result
未知异常 统一返回 B0001，不暴露堆栈与内部信息；日志以 ERROR 记录并告警
traceId 错误响应体与响应头 X-Trace-Id 都带上，便于用户反馈定位

时间 ISO-8601（2026-10-23T08:00:00Z 或带时区偏移）；服务内部统一使用 Instant / OffsetDateTime

#3.6 服务间调用规范

# 规则
1 只能依赖对方的 xxx-api 模块，禁止复制对方的 DTO 或直接写 URL 👀
2 Feign 接口必须指定 contextId 👀；超时默认由平台提供（连接 1s / 读取 3s）🔒，确需调整时按 contextId 单独配置
3 远程调用不得放在数据库事务内（会长时间占用连接）：先调用、后开事务，见 OrderAppService#create 👀
4 不在循环中调用远程接口，提供批量接口（/internal/v1/users?ids=1,2,3）👀
5 禁止服务间循环依赖（A 同步调用 B，B 又同步调用 A）；需要反向通知时用事件 👀
6 调用方通过 infrastructure.remote 中的适配器调用，把下游错误翻译为本服务语义（防腐层）👀
7 同步调用链深度 ≤ 3；更长的流程改为事件驱动 👀
8 新增 /internal 接口同样要做参数校验与鉴权（服务侧也校验 JWT）🔒

#3.7 数据库规范

#3.7.1 基本规则

# 规则
1 一服务一库，禁止跨库访问与跨服务 JOIN 🔒（账号权限只授予本服务库）
2 每张表必须包含公共字段：id BIGINT 主键、created_at、updated_at、deleted、version 🔒（BaseDO）
3 主键使用雪花算法（MyBatis-Plus ASSIGN_ID），不使用自增；不使用 UUID 字符串主键（索引离散）
4 不使用外键、触发器、存储过程；约束在应用层或通过唯一索引实现
5 字符集 utf8mb4（MySQL）；时间列 DATETIME(3) / TIMESTAMP(3)；金额 DECIMAL(18,2) / NUMERIC(18,2)
6 索引命名 uk_<表>_<列>、idx_<表>_<列>；单表索引 ≤ 5 个；联合索引遵循最左前缀
7 禁止 SELECT *（MyBatis-Plus 默认列出字段）；分页单页 ≤ 500 🔒（分页插件限制）
8 禁止无条件的 UPDATE / DELETE 🔒（BlockAttackInnerInterceptor）
9 逻辑删除使用 deleted 字段；唯一索引需考虑已删除数据（必要时把 deleted 设计为删除时间戳并加入唯一索引）
10 单表超过 2000 万行或 50GB 前规划归档 / 分库分表（ShardingSphere 或 PolarDB-X）

#3.7.2 数据库变更（Flyway）

  • 脚本位置：src/main/resources/db/migration/{mysql|postgresql}/，由 spring.flyway.locations=classpath:db/migration/{vendor} 按数据库自动选择 🔒；
  • 命名：V<主版本>_<次版本>_<序号>__<描述>.sql，例如 V1_0_1__outbox.sql；
  • 已在任何共享环境执行过的脚本禁止修改，只能追加新版本（Flyway 校验和会失败）🔒；
  • 变更必须向前兼容，按“扩展 → 迁移 → 收缩”分两个版本完成：先加新列并双写，下个版本再删旧列；
  • 大表 DDL 使用 Online DDL（MySQL ALGORITHM=INPLACE / gh-ost / pt-osc，PostgreSQL CREATE INDEX CONCURRENTLY），由 DBA 在变更窗口执行，Flyway 脚本中记录为已执行；
  • 生产禁止 flyway clean 🔒（spring.flyway.clean-disabled=true）。

#3.7.3 同时支持 MySQL 与 PostgreSQL 时

  • 两套脚本内容等价，CI 中各跑一次集成测试（Testcontainers）；
  • 只使用两者都支持的 SQL：LIMIT/OFFSET、FOR UPDATE SKIP LOCKED、标准 CASE；不使用 ON DUPLICATE KEY UPDATE / ON CONFLICT 等方言（确需时在 Mapper XML 中按 databaseId 分开写）；
  • 布尔 / 状态字段用 SMALLINT/TINYINT 或 VARCHAR 枚举名，避免 BOOLEAN 与 TINYINT(1) 的差异；
  • 项目确定数据库后，删除另一套脚本与驱动，避免长期维护两份。

#3.8 消息规范

# 规则
1 发布事件必须通过 OutboxPublisher，且在本地事务内调用（否则抛异常）🔒
2 消费必须幂等：通过 IdempotentConsumer 或业务唯一约束 👀
3 事件是事实（过去式）：order.created，不是命令 create.order
4 事件契约放在 xxx-api/event，只做向后兼容的修改：可以加字段，不能删除或改名；不兼容时发布新类型 order.created.v2 👀
5 消费方必须容忍未知字段：Spring Boot 默认关闭 FAIL_ON_UNKNOWN_PROPERTIES，不要打开它（OrderCreatedConsumerTest 中有覆盖）
6 事件只携带必要数据（ID + 关键字段），单条消息 < 64KB；大对象传引用（OSS key）
7 需要顺序的事件以聚合根 ID 为 key（Kafka 分区 / RabbitMQ 单活消费者）
8 重试 3 次（指数退避）后进入 DLQ；DLQ 有消息即告警，由补偿工具人工重放 🔒（配置）
9 Topic 由平台以代码方式创建（Strimzi KafkaTopic / 云控制台 / Terraform），应用关闭自动建 topic 🔒
10 消息头使用 acme_event_*，不要使用 ce_ 前缀（会被 Spring Cloud Function 改写）

#3.10 日志与可观测规范

# 规则
1 使用 SLF4J 占位符：log.info("下单成功 orderId={}", id)，禁止字符串拼接
2 级别：ERROR 需要人工处理（会告警）；WARN 可自动恢复的异常；INFO 关键业务节点；DEBUG 调试细节（生产关闭）
3 禁止打印密码、令牌、完整手机号 / 身份证 / 银行卡；请求体日志默认关闭 👀
4 业务异常（BizException）不打印堆栈；未知异常打印一次堆栈（由全局处理器负责，业务代码不要 catch 后再打印）

6 自定义指标使用 Micrometer，命名 acme.<领域>.<指标>，如 acme.order.created；标签基数受控（不要用 userId 做标签）
7 每个服务上线前在 Grafana / ARMS 有大盘，核心接口配置 SLO 告警

#3.11 安全规范

# 规则
1 所有接口默认需要认证 🔒（acme-starter-security）；匿名接口必须显式放行并评审
2 用户身份只从 JWT 的 uid 获取，禁止信任请求参数 / 请求体中的 userId 👀
3 数据级权限：查询“我的”数据时必须带上 uid 条件；不属于当前用户的资源返回 404 而不是 403
4 管理类接口使用 @PreAuthorize("hasRole('ADMIN')")
5 入参全部使用 Bean Validation 校验；SQL 只用 MyBatis 参数绑定（#{}），禁止 ${} 拼接用户输入
6 敏感数据存储加密（手机号、身份证使用 KMS 数据密钥加密 + 哈希索引）
7 镜像扫描（Trivy / ACR）在 CI 中阻断严重漏洞 🔒（deploy/ci/gitlab-ci.yml）；依赖漏洞扫描建议接入 Sonar 或 OWASP Dependency-Check

#3.12 测试规范

#3.13 部署与运行规范

#4.4.3 防腐层：把下游错误翻译成本域语义

java
@Component
public class BuyerGatewayImpl implements BuyerGateway {            // infrastructure.remote
    public boolean canPlaceOrder(Long userId) {
        try {
            Result<UserDTO> result = userClient.getUser(userId);
            return result.isSuccess() && result.data() != null && result.data().isActive();
        } catch (BizException ex) {        // 下游 4xx（用户不存在）→ 不可下单
            return false;
        }                                  // 下游 5xx / 熔断 → RemoteServiceException 原样抛出 → C0001/C0503
    }
}

#4.4.4 灰度负载均衡

java
static List<ServiceInstance> select(List<ServiceInstance> instances, String grayTag) {
    List<ServiceInstance> stable = instances.stream().filter(i -> !StringUtils.hasText(tagOf(i))).toList();
    if (StringUtils.hasText(grayTag)) {
        List<ServiceInstance> gray = instances.stream().filter(i -> grayTag.equals(tagOf(i))).toList();
        if (!gray.isEmpty()) {
            return gray;                   // 带标签的请求 → 同标签实例
        }
    }
    return stable.isEmpty() ? instances : stable;   // 普通请求 → 只走稳定实例
}

通过 @LoadBalancerClients(defaultConfiguration = GrayLoadBalancerClientConfiguration.class) 对所有下游生效，Servlet（Feign）与 WebFlux（网关）分别使用阻塞 / 响应式的服务发现。
